# 任务：重构用户API业务逻辑到Services层

**状态**: 规划中  
**创建时间**: 2025-08-19  
**目标**: 将用户API中的业务逻辑迁移到services层，实现分层架构的最佳实践

## 问题分析

当前 `app/api/v1/user.py` 文件中包含了大量业务逻辑，违反了分层架构原则：

### 需要迁移的业务逻辑组件：
1. **用户认证逻辑** (`authenticate_user`, `hash_password`, `verify_password`)
2. **JWT令牌管理** (`create_access_token`, `verify_token`)
3. **用户数据访问** (`fake_users_db`, `get_current_user`)
4. **配置管理** (JWT配置常量)

### 当前架构问题：
- API层承担了过多责任（违反单一职责原则）
- 业务逻辑与HTTP处理耦合
- 难以进行单元测试
- 不符合项目规范中的分层架构要求

## 执行步骤

- [x] **步骤1**: 分析当前结构，识别需要迁移的组件
- [ ] **步骤2**: 创建services目录结构和用户服务模块
- [ ] **步骤3**: 创建认证服务模块，迁移JWT和密码相关逻辑
- [ ] **步骤4**: 创建用户服务模块，迁移用户管理逻辑
- [ ] **步骤5**: 重构API层，使其仅负责HTTP请求/响应处理
- [ ] **步骤6**: 更新依赖注入和导入关系
- [ ] **步骤7**: 验证重构后功能正常工作

## 目标架构

```
app/
├── api/v1/user.py          # 仅处理HTTP请求/响应，调用services
├── services/               # 新增：业务逻辑层
│   ├── __init__.py
│   ├── auth_service.py     # 认证相关业务逻辑
│   └── user_service.py     # 用户管理业务逻辑
├── core/                   # 新增：核心配置
│   ├── __init__.py
│   ├── config.py           # 配置管理
│   └── security.py         # 安全相关配置
└── schemas/user.py         # 保持不变
```

## 预期收益

1. **更清晰的分层架构**：API层专注HTTP处理，Services层处理业务逻辑
2. **更好的可测试性**：业务逻辑可独立测试
3. **更高的可维护性**：职责分离，代码更易理解和修改
4. **符合项目规范**：遵循推荐的目录结构

## 风险评估

- **低风险**：重构不改变API接口，对外行为保持一致
- **需要注意**：确保依赖注入正确配置，避免循环导入
