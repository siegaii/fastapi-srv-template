# 项目规则

## 核心原则

### 1. 用户意图至上 (User Intent First)
- 用户的明确指令拥有最高优先级
- 所有规则和流程都是为了更好地服务于用户目标
- 如果用户指令与现有文档或代码不同，优先执行用户指令
- 执行后可简要提醒可能的技术债务或影响

### 2. 依据驱动 (Evidence-Driven)
- 所有重要建议必须基于事实和清晰的定义
- 以 `.ai-docs` 中的文档作为事实基线
- 行动必须以已知的基线为起点
- 避免基于假设或猜测的决策

### 3. 状态外化 (Stateful Execution)
- 对于非平凡任务，将思考过程和行动计划完全书面化
- 使用 `.ai-docs/tasks/` 目录管理复杂任务
- 保持任务状态的可见性、可追溯性、可协同性
- 复杂功能应先创建技术笔记梳理思路和设计

### 4. 验证确认 (Verification by User)
- 默认验证方式为用户手动测试
- 提供清晰的验证步骤和预期结果
- 仅在用户明确要求时执行自动化测试
- 确保代码变更的可验证性

### 5. 主动思考与学习 (Proactive Thinking & Learning)
- 主动发现潜在问题和优化点
- 任务完成后进行闭环学习
- 将经验沉淀到项目规则中
- 持续改进开发流程和代码质量

### 6. 情景感知与务实 (Context-Aware & Pragmatic)
- 根据任务规模和复杂度选择合适的流程
- 避免对微小任务进行过度规划
- 平衡完美主义与实用主义
- 优先解决核心问题

## 技术规范

### Python 开发规范

#### 代码风格
- 严格遵循 PEP 8 代码风格指南
- 使用 Black 进行代码格式化
- 最大行长度: 150 字符 (已配置 Pylint)
- 使用有意义的变量和函数名
- 添加适当的注释解释复杂逻辑

#### 类型提示
- 所有函数参数和返回值必须使用类型提示
- 使用 `typing` 模块提供的类型
- 复杂类型使用 `Union`, `Optional`, `List`, `Dict` 等
- 使用 mypy 进行类型检查

#### 导入规范
```python
# 标准库导入
import os
import sys
from datetime import datetime

# 第三方库导入
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

# 本地应用导入
from app.core.config import settings
from app.schemas.user import UserCreate
```

### FastAPI 开发规范

#### 路由组织
- 使用 `APIRouter` 按功能模块组织路由
- 路由文件放在 `app/api/v1/` 目录下
- 每个路由文件对应一个业务领域
- 使用版本化 API 路径: `/api/v1/`

#### 数据验证
- 使用 Pydantic 模型进行请求和响应验证
- 请求模型以 `Request` 结尾，如 `UserCreateRequest`
- 响应模型以 `Response` 结尾，如 `UserResponse`
- 数据传输对象放在 `app/schemas/` 目录

#### 依赖注入
- 使用 FastAPI 的依赖注入系统
- 共享逻辑封装为依赖函数
- 数据库连接、认证等通过依赖注入
- 依赖函数放在 `app/core/deps.py`

#### 错误处理
- 使用适当的 HTTP 状态码
- 统一的错误响应格式
- 自定义异常类继承 `HTTPException`
- 错误信息要清晰且用户友好

### 项目结构规范

#### 目录组织
```
app/
├── __init__.py
├── main.py              # FastAPI 应用入口
├── core/                # 核心配置和依赖
│   ├── config.py        # 配置管理
│   ├── security.py      # 安全相关
│   └── deps.py          # 依赖注入
├── api/                 # API 路由层
│   └── v1/              # API 版本
├── schemas/             # Pydantic 模型
├── models/              # ORM 模型
├── crud/                # 数据访问层
├── services/            # 业务逻辑层
├── utils/               # 工具函数
└── workers/             # 后台任务
```

#### 文件命名
- 使用小写字母和下划线
- 文件名要能反映其功能
- 避免使用缩写，除非是通用缩写
- 测试文件以 `test_` 开头

### 数据库规范

#### ORM 使用
- 使用 SQLAlchemy 作为 ORM 框架
- 模型定义放在 `app/models/` 目录
- 使用 Alembic 进行数据库迁移
- 数据库操作封装在 CRUD 层

#### 查询优化
- 避免 N+1 查询问题
- 使用适当的索引
- 大数据量查询使用分页
- 复杂查询考虑使用原生 SQL

## 开发流程

### 任务分类和处理

#### A. 零仪式通道
- **适用**: 明显的错字修正、注释调整等微小变更
- **流程**: 直接执行，无需额外文档
- **示例**: 修正拼写错误、调整代码格式

#### B. 快速通道
- **适用**: 小功能、简单代码修改或查询
- **流程**: 简单计划 → 执行 → 验证
- **文档**: 在对话中记录计划和结果

#### C. 标准通道
- **适用**: 多数需要追踪状态的常规开发任务
- **流程**: 创建任务档案 → 分步执行 → 状态更新 → 验证
- **文档**: 在 `.ai-docs/tasks/` 创建任务文件

#### D. 提案驱动流程
- **适用**: 架构变更、核心重构、影响多个基线文档的重大变更
- **流程**: 技术提案 → 影响评估 → 分阶段实施 → 文档更新
- **文档**: 详细的技术设计文档和实施计划

### 任务管理

#### 任务状态
- `pending`: 任务未开始
- `in_progress`: 正在进行中
- `completed`: 已完成
- `blocked`: 被阻塞，需要外部输入

#### 任务文件格式
```markdown
# 任务：[简短任务描述]

**状态**: 进行中
**创建时间**: 2024-01-15
**预计完成**: 2024-01-16

## 目标
[描述最终要达成的业务或技术目标]

## 执行步骤
- [x] 步骤 1: [已完成的步骤]
- [ ] 步骤 2: [待执行的步骤]
- [ ] 步骤 3: [待执行的步骤]

## 技术决策
[记录重要的技术选择和原因]

## 遇到的问题
[记录问题和解决方案]

## 验证方式
[描述如何验证任务完成]
```

## 代码质量

### 测试要求
- 核心业务逻辑必须有单元测试
- API 端点必须有集成测试
- 测试覆盖率目标: 90%+
- 使用 pytest 作为测试框架

### 代码审查
- 所有代码变更都需要审查
- 关注代码质量、安全性、性能
- 确保符合项目规范
- 验证测试覆盖率

### 文档要求
- 公共 API 必须有文档字符串
- 复杂算法需要详细注释
- README 文件保持更新
- API 文档自动生成

## 安全规范

### 认证和授权
- 使用 JWT Token 进行认证
- 敏感操作需要权限验证
- Token 设置合理的过期时间
- 实施最小权限原则

### 数据安全
- 密码必须哈希存储
- 敏感信息不能记录到日志
- 使用 HTTPS 传输敏感数据
- 输入数据必须验证和清理

### 配置安全
- 敏感配置使用环境变量
- 不在代码中硬编码密钥
- 生产环境配置与开发环境分离
- 定期轮换密钥和证书
